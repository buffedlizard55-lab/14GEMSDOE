How to make a submission — the exact walkthrough

One file, one Note, two minutes. This page is the executive summary of the submission process: the file format the platform requires, the fastest route to it, and every rejection we have already hit — with the fix.

The 60-second route

  1. Open the Executive summary and click Build submission.tif. Your browser writes the GeoTIFF locally and downloads it as GEMS-…<UTC>-<sha8>.tif.
  2. Copy the Note shown under the button (it is unique to that build).
  3. Go to the competition page → Submit (left sidebar) → Make new submission.
  4. File to submit → choose the downloaded .tif (or the .zip).
  5. Paste the Note into Note (optional) → confirm. Done.

§1 What the file must be

Requirements as printed on the official problem description (source):

RequirementValueChecked by
Formatsingle-band GeoTIFF (.tif), or a .zip with one GeoTIFFform text
CRSUTM zone 11N — EPSG:32611scripts/validate_submission.py
Resolution100 msame
Shape / boundssame as the training data — 3,292 × 3,730 px; data outside the bounds is null or NaNsame
Band type32-bit float (float32), single layersame
Valuesprobabilities in [0, 1]; higher = more likely faultsame

§2 Four ways to produce the file

  1. From this site — one click (no install; validated at build time).
  2. From the pipeline — python3 scripts/build_submission.py artifacts/pred.npy --policy "<run id>" → writes submissions/GEMS_<policy>_<UTC>_<sha8>.tif plus a .NOTE.txt and a .MANIFEST.json (hash, value histogram, clip counts) and refuses to emit a file that would be rejected.
  3. From the reference-style notebook — any float32 raster on the template grid can be pushed through scripts/validate_submission.py and uploaded.
  4. Max-compatibility variant — identical predictions with 0.0 outside the footprint and no NaN anywhere (--zero-outside / the third button). Under the official scoring equations NaN-outside and 0-outside are equivalent; use this variant only if the form has already rejected the NaN variant (§6).

§3 Unique names and Notes — no more indistinguishable submissions

Every build is named GEMS_<policy-slug>_<UTC>_<sha8>.tif where sha8 is the first 8 hex digits of the file's SHA-256. Two builds of different pixels can never share a name, and the manifest proves which pixels were uploaded. The Note field mirrors it:

S5-A · relay-corridor ensemble r7 · heldout DTI 0.31 · sha8=05256bf5

Convention: <run> · <what is new> · <holdout number> · sha8.

§4 What is scored (why “predicting the known faults” scores ~0.156)

Official staff ruling — forum thread 11516 (2026-09-16, DrivenData staff): “Pixels corresponding to known USGS/INGENIOUS faults are masked / excluded from evaluation, so they do not count towards penalty terms.” Including the catalogue in your prediction is free but earns nothing — the entire score comes from your off-catalogue predictions near the hidden new faults.

§5 Budget and selection rules

  • 3 submissions per week per entity (rules §3.2/§3.4 — official rules PDF).
  • By the deadline you must choose one submission to be scored in both prize rounds (rules §3.5) — chosen without knowing your private-test score (§3.6.2).
  • Phase 1 ($50,000, top 5 × $10,000) scores against the private new-fault set; Phase 2 ($250,000) re-scores the same file against labels expanded by expert review of everyone's predictions.
  • Finalists submit complete code + documentation (rules §3.5) — this repository is structured to be that deliverable.

§6 “Predicted values must be in range [0, 1]” — what it means and how to fix it

The form's range check reads your raster's values. Three mechanical causes trip it (all reproduced and caught by tests/test_submission_gate.py):

CauseSymptomFix
Values outside [0, 1] — raw scores/logits, or 0–255 bytes min < 0 or max > 1 in the manifest build_submission.py clamps to [0, 1] and reports how many pixels were clipped; better: pass calibrated probabilities
NaN anywhere in the raster — including the nodata outside the footprint. The format page permits “null or NaN” outside, but a real upload attempt on 2026-09-28 with a NaN-outside file was rejected with exactly this error, so the checker tests all pixels, not just the footprint (TEAM-REPORTED evidence; recorded as FLAG #10) your file has GDAL_NODATA=nan and NaN pixels use the site's default download (finite: 0.0 outside, no NaN) — or build_submission.py's finite output. 0.0 outside cannot change the score: no labels exist there and 0.0 is below any threshold
NaN inside the scored region (holes in the prediction) “NaN in: n filled” after --fix-nan run with --fix-nan (fills holes with 0.0), or use the site's default finite download

Nothing else about the container (deflate compression, EPSG tag form) has triggered a rejection in our runs; if a new message appears, record it verbatim in research/limitations_and_next.md before changing anything.

§7 Pre-flight checklist

  • ☐ File name carries its own sha8 and policy slug.
  • ☐ Note pasted and matches the run (policy · holdout DTI · sha8).
  • ☐ validate_submission.py says PASS (or the site build log shows every self-check green).
  • ☐ This run beat the current best on the spatially-blocked holdout before it was allowed to use a weekly slot.
  • ☐ The week's budget (≤ 3) is being spent deliberately; slot #3 is a control only when its purpose is written down first.
