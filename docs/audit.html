Artifact audit — why 0.1563 kept appearing

The question was blunt: are we copying the same work over and over? The answer is now measurable, because every scored artifact the group ever uploaded is available as a file. This page reports the hashes, the pixel comparisons, and exactly what is proven versus merely inferred.

Result in one line. GEMSDOE and 5GEMSDOE published byte-identical submission files (same git blob SHA-1, same 570,890 bytes, same SHA-256) — so if both accounts uploaded what their sites publish, the identical score is not a coincidence, it is the same pixels. The group's eight other scored artifacts are all different prediction arrays; the real defect was not duplication of files but duplication of idea: eight fields, one emission style, two of them 94 % overlapping.

A git blob SHA-1 is a content hash. Identical values mean identical bytes, independent of timestamps or commit history. Reproduce with:

python3 scripts/audit_scored_artifacts.py --fetch-scored
# or against the vendored copies:
python3 scripts/audit_scored_artifacts.py /path/to/external/scored/*.tif \
        --json artifacts/scored_artifact_audit.json

What this does not prove: which file each account actually uploaded. DrivenData submission IDs and upload binaries exist in none of the group's repositories. Artifact-level identity is proven; upload-level identity is inferred from group records. Nothing on this page claims more than that.

8 files, 8 distinct prediction arrays. The group has not been re-uploading one raster. Two qualifications matter:

  1. #2 and #3 are near-duplicates in content — Jaccard 0.94 on their positive-pixel sets, scores 0.1563 vs 0.1560. Different bytes, same idea, 0.0003 apart.
  2. Every field is binary and thin (mass equals the number of positive pixels; 1.2–5.1 % of the 5.17 M-pixel footprint). The metric algebra (see round 5) shows binary emission is right given a support, so the whole history has been a search over supports — at a frozen emission style.

3. What the scores reveal

  • Selection moves the score; budget does not. The three "pindrop" submissions used an identical budget of exactly 155,021 pixels and scored 0.0830, 0.1152 and 0.1193 — a spread of 0.036 from nothing but the spatial choice, larger than any feature round the group has run.
  • Catalogue-hugging is the worst strategy. The field with 73 % of its mass inside 300 m of the catalogue scored 0.0286; fields with 8–20 % catalogue overlap scored 3–4× higher. The scored population is the catalogue's complement (staff ruling: known USGS/INGENIOUS pixels are masked and excluded from evaluation).
  • A single submission can move 40 places. In the live leaderboard refresh during this session, op01 went 0.1293 → 0.2489 (#44 → #7) — so the plateau is an emission-policy problem, not a data problem.

5. How a repeat can now never happen

  • Every build gets a unique name with the UTC timestamp and the artifact's own hash: GEMS_<policy>_<UTC>_<sha8>.tif, plus a NOTE.txt (the exact text for the DrivenData Note field) and a MANIFEST.json (policy, histogram, pixel SHA-256).
  • scripts/check_submission_uniqueness.py compares the prediction-array SHA-256 against every prior artifact and hard-fails on a collision — a repeated rounded score is only a warning, because a rounded score is not evidence of identity.
  • The submission pipeline refuses to write a file with non-finite values or values outside [0, 1] — the exact rejection ("Predicted values must be in range [0, 1]") a teammate hit with a NaN-nodata upload.
